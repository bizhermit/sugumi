# 0006. `script-src` を nonce + import map ハッシュのみで構成した技術的裁定

## 状況

本書はバンドラを使わず素の ESM を配信する（P3）。エントリの
`<script type="module" src="…" nonce="…">` は nonce で許可されるが、そこから
`pages` → `components` → 基盤と連なる**静的 import のサブリソースにも `script-src` の照合が掛かる**。
ここを許可するソース表現が1つも無いと、層2/層3 が丸ごと消えて層1に落ちる。CSP 違反はブラウザの
コンソールにしか出ないため、サーバーログにも Node だけの統合テストにも一切現れず、本書で最も発見が
遅れる事故クラスになる。

フェーズ0の時点では、3つの候補（案X `'strict-dynamic'`、案Y パス限定ホストソース、案Z `'self'`）が
いずれも機能的に成立するという前提のもと、**最も許可が狭いという理由で案Y（パス限定ホストソース）を
暫定採用**していた（旧裁定14）。sec-audit もこの選定を支持していたが、**実測前の暫定**という位置づけで
あり、付録B-11 が「(a) が通ったら（パス限定ホストソースを使わない構成が動くことが確認できたら）外すのが
既定」と定めていた。フェーズ1で実測（付録B-11・F27）を実施した結果、パス限定ホストソースを一切置かない
構成（nonce + import map ハッシュのみ）でもエリアを跨ぐ静的 import 連鎖が問題なく解決・実行されることが
確認され、利用者が再裁定を行った。

## 決定

**`script-src` は `'nonce-…'`（リクエスト毎）と import map のハッシュ `'sha256-…'` の2要素だけで構成する。**
パス限定ホストソース・`'self'`・`'strict-dynamic'` のいずれも置かない。

```
script-src 'nonce-<リクエスト毎>' 'sha256-<import map・起動時に算出>';
```

- 実装は `src/platform/server/csp/buildCsp(nonce, importMapHash)` の1関数に集約し、`ServiceDef` を
  引数に取らない（サービス側に組み立てさせない）。
- `<script>` には（`src` 付き・インライン問わず）必ず nonce を付ける。付け忘れたスクリプトは
  確実に実行されない。インライン `<script>` は import map 以外に書かない（§5.6）。
- `ServiceDef.assetNamespaces`（§15.2）は CSP の正本ではなくなり、静的配信の許可範囲（§6.6）の
  正本としてのみ残る。

## 理由

**実測（F27・2026-08-10）**: `script-src 'nonce-…' 'sha256-…'` のみの構成で、エリアを跨ぐ import 連鎖
（`pages` → `components` → 基盤）が bare specifier / 相対 import の両方で解決・実行された（CSP 違反
0件）。HTML 仕様の *descendant script fetch options* が親スクリプトの cryptographic nonce を子モジュール
へ引き継ぐ、という本書の前提が実測で裏づけられた。**陰性対照（`script-src 'none'`）では実際に違反が出て
スクリプトが実行されなかった**ことも併せて確認しており、「常に成功と判定する測定」ではないことを担保した
（付録A F27・§12.5-M1）。パス限定ホストソースを足した構成・`'strict-dynamic'` を足した構成でも同様に
成功しており、3構成いずれも技術的には成立する。

- **nonce 無しで実行できる範囲がゼロになった。** これが本構成を採る決め手である。旧・案Y（パス限定
  ホストソース）は「許可ディレクトリ配下が nonce 無しでも実行できる」という固有の代償を持っていた。
  実測の結果その代償を払う必要が無いと判明したため外した。
- **選定基準は許可の狭さ**であり、3構成のうち nonce + ハッシュのみが最も狭い。
  - `'self'`（旧・案Z）は同一オリジンの**任意のパス**を許す。
  - `'strict-dynamic'`（旧・案X）は「信頼済みスクリプトが読み込むもの」を**出所を問わず**許す。
  - nonce + ハッシュのみは、**そのリクエストで発行した nonce を持つスクリプトしか実行を許さない**。
- **消えた保守コスト**: 旧構成では CSP を `assetNamespaces` から生成する必要があり、サービスの依存が
  増えるたびに `script-src` の行が増えた。本構成では `script-src` はどのサービスでも同一の2要素であり、
  サービス数にも依存数にも比例しない。

## 影響

- **§12.4-33 の検査 (a)(b) が置換された。** 2026-08-10 の裁定より前は「パス限定ホストソースの集合が
  `assetNamespaces` の展開と完全一致すること」を検査していたが、ホストソースを置かなくなったため前提
  ごと消えた（実測 F27）。置き換えた形は `script-src` が `'nonce-…'` と `'sha256-…'` の2要素だけである
  ことと、文書内の全 `<script>` に `nonce` 属性が付いていることを検査する。この (b) の検査は**新構成で
  新たに意味を持つようになった**（旧構成では許可ディレクトリ配下なら nonce 無しでも動いてしまい付け
  忘れが露見しなかったため、緩和ではなく強化である）。
- **§15.2 の `assetNamespaces` は、静的配信の正本としては残るが CSP 導出の正本ではなくなった。**
  この分離は防御の後退ではない。他サービスの資産が実行される経路は (1) §6.6 が名前空間外を 404 に
  する、(2) nonce の無いスクリプトは実行されない、の二重で塞がれている。旧構成が CSP 側で名前空間を
  列挙していたのは nonce 無し実行を許す範囲があったためであり、その範囲が消えた以上、列挙する対象自体
  が無い。
- **サービス数に比例して増える CSP の保守コストが消えた。** 1プロセスに複数サービスをマウントする
  場合（§15）も CSP はレスポンス単位のまま変わらないが、値が同一になるためサービスごとに別の値を
  組み立てる必要が無い（nonce だけがリクエスト毎に変わる）。
- **`--allow-fs-write` を `dist/` / `public/` に与えてはならない理由が変わった（重要な二次効果）。**
  従来の根拠は「`dist/<エリア>/client/` が CSP で実行を許可されたディレクトリだから、書き込みを
  許すと自分の配信する実行可能 JS を書き換えられる」というものだった。**この根拠はこの裁定により
  偽になった。** nonce 方式では CSP は「どのファイルか」ではなく「nonce を持つか」しか見ないため、
  **攻撃者に書き換えられた `.js` であっても、応答時に正規の nonce が付与されれば CSP では止まらない。**
  すなわち「CSP があるから書き換えを防げる」という期待はこの裁定以降まったく成立しない。
  `--allow-fs-write` を `DATABASE_PATH` とその兄弟ファイルだけに絞る規約（§6.5・0008 参照）は、
  この点で**唯一の防衛線**になった。§6.5 は根拠をこの形に差し替え済みであり、この ADR にも二次効果を
  明記するのは、「CSP があるから改ざんは防げる」という誤った安心が後から復活しないようにするためである。
- **静的配信がリダイレクトを返さないという §6.6 の規約（§12.4-33(d)）は本構成でも維持する。** 旧構成
  では「パス付きホストソースの照合がリダイレクトで外れる」ことが理由だったが、その理由は消えた。
  それでも維持するのは、リダイレクトを返す静的配信が §6.6 のパス解決とキャッシュ制御を複雑にする
  ためであり、根拠が §6.6 側の理由に差し替わった。
- **`CSP_EXTRA_SCRIPT_SRC` に相当する設定キーは存在しない**（Q39 で既に廃止済み）。本構成により、
  `script-src` は設定値の影響を一切受けず、本書の記述だけで完全に決まる。

## 却下した代替案

- **案X（`'strict-dynamic'`）**: 実測では import 連鎖の解決に成功したが、「信頼済みスクリプトが動的に
  読み込んだものを出所を問わず実行できる」という許可を追加する。本書は静的 import しか使わない（P3）
  ため、この緩和で得られる機能が無く、許可が広がるだけで得るものが無いため却下した。
- **案Y（パス限定ホストソース。旧暫定採用）**: フェーズ0時点では「最も許可が狭い」との理由で暫定
  採用していたが、「許可ディレクトリ配下は nonce 無しでもスクリプトとして実行できる」という固有の
  代償を持つ。実測（F27）で nonce + ハッシュのみの構成でも成立することが確認され、その代償を払う
  必要が無いと判明したため却下（外す）した。さらに、この構成は CSP を `assetNamespaces` から都度
  導出する必要があり、サービスの依存が増えるたびに保守コストが増える欠点もあった。
- **案Z（`'self'`）**: 実測では import 連鎖の解決に成功したが、同一オリジンの**任意のパス**を許す
  ため3案の中で最も広い。許可の狭さを選定基準とする以上、最も広い案を採る理由が無く却下した。
