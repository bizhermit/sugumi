# 0004. 複数マイクロサービス集合リポジトリ構成、`src/` 配置、`db/` の分離

## 状況

sugumi は当初「変更禁止の制約」として `/client` `/server` `/shared` の3プロジェクト参照構成を前提に
していた（§1.1 X7）。フェーズ0の途中で、制約の設定者本人（利用者）が「各マイクロサービス間で部品を
共有可能にしたい。基盤レイヤーは共通としてよい」との裁定を下し、構成そのものを複数マイクロサービスの
集合リポジトリへ変更した。制約の設定者本人による変更であるため、これは規約からの逸脱ではない。

この変更に伴い、次を追加で決める必要が生じた。

- サービス間で共有する部品の置き場所と依存方向。
- ビルド対象ツリー（`src/`）をリポジトリ直下に単一で置くか、エリアごとに置くか。
- CSS・SQL 等トランスパイル対象でない資材の置き場所。
- プロジェクト間の import specifier の解決方式（npm workspaces を使うか）。
- 複数サービスをどう実行するか（1プロセス1サービスか、1プロセス複数サービスか）。

## 決定

**複数マイクロサービスの集合リポジトリ構成へ変更する**（§2.1）。

```
sugumi/
├─ src/
│  ├─ platform/{shared,server,client}/   全サービス共通の基盤。業務知識を持たない
│  ├─ packages/<name>/{shared,server,client}/  サービス間で共有する業務部品
│  ├─ services/<name>/{shared,server,client}/  1ディレクトリ = 1マイクロサービス（単体でもここ）
│  └─ hosts/<name>/main.ts               1ディレクトリ = 1プロセス。唯一の合成ルート
├─ public/  db/  tests/  docs/  dist/
└─ package.json / tsconfig.json 他
```

- **サービスは単体でも常に `src/services/<name>/` 配下に置く**（後から増やすときに移動が発生しない）。
- **サービス間共有は2層**: `platform`（全サービス共通の基盤。業務知識を持たない）と `packages`
  （サービス間で共有する業務部品）。依存方向は `services → packages → platform` の一方通行、
  `packages` 同士・`services` 同士の import は禁止する（§2.2）。
- **`src/` はリポジトリ直下に単一で置き**、4エリア（`platform` / `packages` / `services` / `hosts`）を
  その配下に収める。エリアごとの `src/`（`services/<name>/src/…`）にはしない（§2.1）。
- **`src/` に置くのは `.ts` と各プロジェクトの `tsconfig.json` だけ**とする。CSS は `public/`、
  SQL スキーマは `db/` へ、トランスパイル対象でない資材はすべて `src/` の外に出す。
- **プロジェクト間の import は単一の `package.json` + `exports`（エリアごとに1エントリ、計4つ）**で
  解決する。npm workspaces は採用しない（§10.5）。
- **実行単位はサービスではなく `src/hosts/<name>/`**。既定はサービスごとに host を1つ（1サービス
  1プロセス・独立ポート）、複数サービスをまとめたい場合は複数マウントする host を別途追加する
  （既存の host を書き換えない）。複数マウント時も「サービスごとに別々の `node:http` サーバーを
  別々のポートで listen する」方式を採り、パス接頭辞によるマウントは採らない（§15）。
- **参照実装は2サービス（`app` / `admin`）＋ `packages/` の実例1つ（`packages/user-profile`）とする。**

## 理由

- **`hosts/` を独立エリアとして切り出す**: プロセスの単位を `services/` から分離しないと、「1プロセス
  複数サービス」を実現するために複数サービスを同時に import できる場所が `services/` 内に必要になり、
  「services 同士の import 禁止」が最初から破れる。`hosts/` を切り出すことで、サービス同士の相互
  import 禁止を例外なしで機械検査できる（§12.4-1）。
- **直下単一の `src/`**: `package.json` の `exports` は自己参照 specifier 1エントリにつきワイルドカードを
  1つしか書けない。エリアごとの `src/`（`services/<name>/src/…`）にすると、サービス名で1つ・
  `src/` 以下のパスでもう1つのワイルドカードが必要になり成立しない。直下単一の `src/` なら
  ワイルドカードは1つのまま成立する。実測（TS 7.0.2 / Node 26.5.0）で `tsc --build --force` が
  exit 0、`dist/` の形が移行前と同一、`node`（既定条件）と `node --conditions=development`
  の両方で解決に成功することを確認した。
- **npm workspaces を採用しない**: `development` 条件（テストがソースの `.ts` を解決する仕組み）の
  正本を package の数だけ複製することになり、1つでも書き忘れると「`dist` の古い成果物をテストして
  緑になる」というサイレントな誤合格が復活する。またサービス追加のたびに lockfile が変わり、
  §11.6 の「`npm ci` のみ・`npm install` による lockfile の暗黙更新を禁止」という規約と衝突する。
  workspaces が解く問題（パッケージごとに異なる依存を管理する・個別に npm 公開する）も本件には
  存在しない（runtime 依存ゼロ・`private: true`）。「実行時に `node_modules/` の読み取り許可が
  不要になる」点は副次的な利点にすぎず、裁定の主たる根拠にはしない（実際に `--allow-fs-read` の
  許可範囲を広げうるのは workspaces ではなく中間ワイルドカード。実測 F16。0008 参照）。
- **1プロセス複数サービスをポート分離で行う**: パス接頭辞方式は `BASE_URL`・`__Host-` Cookie が要求する
  `Path=/`・CSRF の Origin 検証（0007）・静的配信の名前空間・`form-action`・オープンリダイレクトの
  相対パス判定のすべてに「接頭辞を考慮する」分岐を持ち込み、どれか1つを書き忘れた瞬間にサービス間の
  境界が壊れる（あるサービスのセッション Cookie が別サービスへ送られる等）。ポート分離ならサービスから
  見た世界は「1サービス1プロセス」と完全に同一で、規約の分岐がゼロになる。ただし Cookie はポートでは
  分離されない（RFC 6265 §8.5）ため、この一点は公開形態の規定とセッション Cookie 名のサービス単位化で
  別途塞ぐ（§15.3・§15.6）。
- **参照実装を2サービス構成にする**: サービスが1つしか無いと、`services` 同士の import 禁止・
  サービス単位の静的配信の許可範囲（`ServiceDef.assetNamespaces`。§6.6）・全サービス走査の検査・
  セッションの非越境が一度も実物で検証されないまま納品されてしまう。（この裁定の時点では CSP も
  サービス単位に組み立てる設計だったため検証対象に含めていたが、後の 0006 の再裁定で `script-src`
  は全サービス共通の値になった。それでも静的配信の許可範囲はサービスごとに異なる宣言のままであり、
  2サービス構成で検証する意義は変わらない）

## 影響

- tsconfig プロジェクトの本数はサービス数に比例して増える（一般形 `5 + 3×(1+P+S) + H`。参照実装は
  P=1 / S=2 / H=3 で20本）。テスト用 tsconfig（shared/server/client）はレイヤーだけで決まるため
  3本のまま増えない。
- import specifier の形は `sugumi/<エリア>/<レイヤー>/…` の4通りに固定され、依存方向の機械検査
  （§12.4-1）は specifier の先頭セグメントだけで判定できる（AST 解析を要しない）。
- 静的配信（§6.6）の許可範囲は `ServiceDef.assetNamespaces` を正本として導出する（0008 参照）。
  **CSP（§9.1）はこの宣言からは導出しない**（0006 の再裁定により `script-src` は nonce + import map
  ハッシュのみの全サービス共通値になったため。「配信してよい範囲」と「実行してよい範囲」は別々の
  根拠で守られる。二重管理ではない）。
- サービス追加は「ディレクトリ + tsconfig + ルート `references` 1行」の3点で完結し、`package.json` も
  lockfile も動かない。

## 却下した代替案

- **当初の3プロジェクト構成（`/client` `/server` `/shared`）の維持**: 制約の設定者本人が
  「各マイクロサービス間で部品を共有可能にしたい」との要望により変更を裁定したため、この案は
  現行要件を満たせず却下した。
- **エリアごとの `src/`（`services/<name>/src/…`）**: `package.json` の `exports` の自己参照 specifier
  はワイルドカードを1エントリにつき1つしか書けず、この構成では成立しないため却下した（上記「理由」参照）。
- **npm workspaces の採用**: `development` 条件の正本の複製・サービス追加のたびの lockfile 変動・
  workspaces が解く問題（個別 npm 公開等）が本件に存在しないことの3点により却下した。
- **1プロセス複数サービスをパス接頭辞（`/admin/**` 等）でマウントする**: `BASE_URL`・Cookie の
  `Path`・CSRF の Origin 検証・静的配信・オープンリダイレクト判定のすべてに接頭辞を考慮する分岐が
  必要になり、書き忘れがサービス間境界の崩壊に直結するため却下した。パス接頭辞で見せたい場合は
  リバースプロキシ側で行う運用とした（アプリはポートだけを知る）。
