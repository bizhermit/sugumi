# 0001. 依存ゼロ方針と、runtime 依存・devDependencies の例外判定基準

## 状況

sugumi は「フレームワークなし・runtime 依存なし・Web プラットフォームの標準機能だけを使う」ことを
価値の中心に据えたテンプレートである（変更禁止の制約 P1〜P11。うち P2 が「runtime dependencies は
原則ゼロ。例外は外部サービスとの通信境界のみ」を定める）。

制約 P2 は runtime dependencies（成果物が実行時に読み込む依存）の話であり、devDependencies
（`typescript` 等の開発ツール）の可否は当初 P11 の暗黙の前提任せで、判定基準を持たなかった。
フェーズ0で `@types/node`（0002 参照）と整形ツール `@biomejs/biome`（0005 参照）を devDependencies に
追加する必要が生じ、「開発ツールなら何でも良い」への滑り出しを止める明文の基準が要るようになった。

## 決定

**runtime dependencies** は次の4条件を AND ですべて満たす場合のみ、例外として ADR を経て認める（§3.1）。

1. プロセス外の独立したサービス（DB・キャッシュ・メール・オブジェクトストレージ・決済等）と通信する。
2. 相手側のプロトコル / ワイヤフォーマット / 認証手順が自プロジェクトの管理外で、追従が必要。
3. `node:*` と Web 標準 API（`fetch` 等）だけでは実用的に実装できない。
4. ADR に transitive dependency の一覧と件数（`npm ls --all` の実測値）を記載している（上限は設けない。
   手続要件として「判断を隠さない」ことを担保する）。

**devDependencies**（開発ツール）は別の基準として、次の3条件を AND ですべて満たすものだけを許す（§1.1）。

1. **成果物に入らない** — `dist/` と配信物に1バイトも現れない。
2. **ビルドに参加しない** — `dist/` を作るのは `tsc` だけ、という P3 を侵さない。
3. **1コミットで外せる** — 外してもソースコードの意味が変わらない（依存1行・設定ファイル・
   `scripts` 1〜2行の削除で済む）。

追加は必ず ADR を起票し、devDependencies の場合は依存パッケージ数（推移的依存を含む実測値）・
ライフサイクルスクリプトの有無・ネイティブバイナリの配布方式・実行タイミングと実行環境の4点を
必ず記載する（この4点は `@biomejs/biome` の採否評価で実際に測定した項目そのものである。0005 参照）。

## 理由

- **旧基準「実行時コードを1バイトも含まない」は整形ツールに適用できない。** 整形ツールはネイティブ
  バイナリを含み、開発者のマシンで実際に実行される（0005 参照）。理由が事実と食い違う規約は
  §0.3「理由が書けない規約は規約にしない」に抵触するため、devDependencies の判定軸そのものを
  runtime dependencies とは別に立てた。
- 3条件のセキュリティ上の読み方（sec-audit の評価）: 条件1・2は「利用者が実行するコードに第三者製
  ツールのコードが混入しない」＝成果物の完全性の境界であり、侵害された devDependency が到達できる
  範囲を開発機と CI に閉じる。条件3は単独ではセキュリティ境界ではないが、切り離し可能性の担保として
  意味を持つ。
- **3条件は「そのツールが何を・いつ・どの権限で実行するか」を問うていない。** 3条件を満たしたまま、
  作業ツリー全体と CI のシークレットに触れるネイティブバイナリを毎コミット実行するツールも追加できて
  しまう（`--ignore-scripts` が止めるのはライフサイクルスクリプトだけであり、`tsc` 実行時に動く
  ネイティブバイナリは止まらない。実測 F7）。この穴は ADR の必須記載（依存数・スクリプト有無・
  配布方式・実行タイミング）で埋める。
- runtime dependencies の4条件は、外部サービスとの通信境界という P2 の例外をなし崩しにしないための
  歯止めである。条件4（transitive dependency 数の明記）は「多いか少ないか」を人の裁量で判断させず、
  事実を明示したうえで ADR の場で採否を判断させる手続要件とした。

## 影響

- devDependencies の追加提案は、まず「成果物に入るか」「ビルドに参加するか」「1コミットで外せるか」の
  3点で機械的に足切りできる。バンドラは条件2で、テストランナー（Vitest 等）は条件3で、統合ツール
  チェーン（Vite+ 等）は条件2・3の両方で落ちる（判定例は §1.1 の表）。
- runtime dependencies の追加提案（PostgreSQL / MySQL ドライバ、Redis クライアント、SMTP クライアント、
  クラウド SDK 等）は、4条件のいずれかを満たさない限り却下する。ユーティリティ（lodash / date-fns）・
  バリデータ（zod 等）・ロガー・HTTP フレームワーク・テンプレートエンジン・UUID・パスワードハッシュ・
  SQLite・JWT・テストランナー・DOM 実装（jsdom）は明示的に非該当とする（§3.1）。
- `docs/decisions/` に記録の無い runtime 依存の追加は禁止する。今後の依存追加提案はこの ADR の
  判定基準に照らして起票する。

## 却下した代替案

- **旧基準「実行時コードを1バイトも含まない」の維持**: `@types/node` は正当化できるが、整形ツール
  （ネイティブバイナリを実行する）を正当化できず、devDependencies を実質2つに固定したまま整形の
  機械的担保を諦めることになる。§0.4「レビュー依存の規約は腐る」の唯一の例外を放置する結果になるため
  却下した。
- **「Prettier だけを例外にする」形の個別許可**: 次の例外を断る根拠が無くなり、devDependencies が
  際限なく増える滑り出しを止められないため却下した。
- **devDependencies の可否を都度レビューで判断する（明文の基準を持たない）**: 判定を人の裁量に委ねると
  必ず緩む、という §3.1 の runtime 依存に対する判断と同じ理由で却下した。
