# 0007. CSRF を SameSite=Lax + Origin 検証で構成（2026-08-10 利用者追認により確定）

## 状況

規約の策定過程で、CSRF 対策の方式が出典（フェーズ0初期の検討メモ）では「層1と共通のトークン方式
（同期トークンパターン）」とされていたものが、統合の過程で「SameSite=Lax + Origin 検証」へ変更された。
この変更は要確認としても ADR としても記録されないまま本書 §9.2 に「確定規約」として反映されていた
（sec-audit 指摘 M-14）。§0.2 の規則により、セキュリティ規約は暫定であれば必ず「暫定」または
「要確認 Qn」を明示しなければならない。この変更が出典からの無記録の変更である以上、**利用者の追認を
得たうえで ADR として記録する**必要が生じ、本書 §9.2 に **要確認 Q41** として起票されていた。

**2026-08-10、利用者は Q41 を追認した。** 採否は「SameSite=Lax + Origin 検証で確定し、層1と共通の
トークン方式には戻さない」であり、根拠は sec-audit の「本節の fail-closed を徹底すればトークン方式は
不要」という判断である。これにより §9.2 の要確認 Q41 は解消され、以下は現行方式（SameSite=Lax +
Origin 検証）を採用するに至った経緯と根拠、および追認により確定した内容の記録である。

## 決定

**CSRF 対策は SameSite=Lax + Origin 検証の二重防御とする**（§9.2）。

- 安全でないメソッド（POST / PUT / PATCH / DELETE）は、`Origin` ヘッダが存在し、かつ
  `new URL(BASE_URL).origin` と完全一致する場合のみ受理する。次はすべて 403 で拒否する
  （fail-closed。「無ければ通す」を作らない）。
  - `Origin` が欠落している
  - `Origin: null`
  - `Origin` が複数値
  - `Origin` は在るが不一致
- 比較は `URL` でパースした `origin` 同士の厳密一致で行い、前方一致・部分文字列一致・`startsWith`
  は禁止する。`Referer` へのフォールバックは行わない。`Host` ヘッダは信用せず、突き合わせ先は常に
  設定値 `BASE_URL` とする。
- `Content-Type` も検査し、POST は `application/x-www-form-urlencoded` のみ受理する。
- 層2の `fetch` 経路にも例外を作らない（`X-Partial` の存在をもって検証を緩めない）。
- 「GET は副作用を持たない」ことを二重の検査（静的検査 §12.4-20・統合テスト §12.4-32）で担保し、
  トークン方式に依存しない設計とする。

## 理由

- **sec-audit の判断**: 「本節の fail-closed（`Origin` の欠落・`null`・複数値・不一致をすべて 403、
  `Referer` フォールバック無し、`Content-Type` 検査併用）を徹底すればトークン方式は不要」とする
  評価を得ている。
- **`SameSite=Lax` 単独の弱点を Origin 検証が補う**: `SameSite=Lax` はサブドメインを同一サイトと
  みなす。`evil.app.example` を攻撃者が取得できる、あるいはそこに XSS がある場合、`SameSite=Lax`
  だけでは CSRF が成立しうる。Origin の完全一致検証がこれを塞ぐ。これが「二重防御」と呼ぶ実質的な
  理由である。
- **追加コストがほぼゼロ**: 現行ブラウザは `<form>` の通常送信でも `Origin` を送るため、fail-closed
  を徹底しても層1で拒否は起きない（フェーズ4の統合テストで層1経路を検証する。§12.4-24/25）。
- **トークン方式は保守負担が大きい**: トークンの生成・埋め込み・検証・失効・多重タブでの扱いを
  すべて自作することになり、§7.4 の `_submission_id`（POST 冪等性トークン。別途要確認 Q38）と
  機構が重複する。
- **`Origin` を送らない環境からは利用できなくなる（403 になる）** 点は仕様として残るが、`Origin` を
  送らない古い環境は `SameSite=Lax` も未サポートであることが多く、その環境では二重防御の2層が
  そもそも同時に外れるため、Origin 検証を緩めて片方だけを残す判断は採らない。

**OWASP CSRF Prevention Cheat Sheet の第一推奨（トークン方式）との差（2026-08-11 利用者追認・裁定46）**

OWASP CSRF Prevention Cheat Sheet は、CSRF 対策の第一推奨として Synchronizer Token Pattern（同期
トークンパターン。セッションに紐づく予測不能なトークンをフォームに埋め込み、サーバー側で検証する
方式）を挙げ、`SameSite` Cookie 属性は Defense in Depth（多層防御の補助策）として位置づけている。
**本 ADR が採用する SameSite=Lax + Origin 検証は、OWASP が第一推奨とするトークン方式そのものを
実装していない。**

**差を許容した理由**:
- sec-audit が「本節（§9.2）の fail-closed を徹底すればトークン方式は不要」と判断し、2026-08-11 に
  利用者がこの判断を追認した（裁定46）。追認の対象は「SameSite=Lax + Origin 検証で確定し、トークン
  方式には戻さない」という採否そのものである。
- **依存ゼロ・実装最小というテンプレートの性格**も理由に含まれる。トークン方式は生成・埋め込み・
  検証・失効・多重タブでの扱いを自作することになり（上記「理由」節のとおり）、§7.4 の POST 冪等性
  トークンと機構が重複するうえ、fork 利用者が最初に触れる実装量を増やす。SameSite+Origin 検証は
  `node:http` と Web 標準 API だけで完結し、追加の実装面が無い。

**どういう場合にトークン方式へ切り替えるべきか（fork 利用者向けの判断材料。0009 の「fork 利用者が
自分の実機で測り直して引き上げられる手順」と同じ役割）**:
1. `Origin` ヘッダを送らない、または信頼できないクライアント（一部の非ブラウザ HTTP クライアント・
   `Origin` を剥がすプロキシ経由のリクエスト等）を正規の利用者として救済する必要がある場合。
   fail-closed 設計ではこれらは一律 403 になるため、救済にはトークン方式の追加が要る。
2. §15.6 の形態B（単一ホスト名 + パス分け）で、同一オリジンであるが故に Origin 検証が素通しになる
   場合に、B-1/B-2 の対策では足りないと判断し、追加の防御層を足したいとき。
3. コンプライアンス・監査要件が OWASP 第一推奨の実装そのものを要求する場合。
4. 将来 Origin 検証の fail-closed を緩める改訂を行う場合（§9.2 が明記するとおり、この前提が崩れる
   改訂を入れるならトークン方式の再検討が必須になる）。

いずれかに該当する場合は、下記「却下した代替案」の評価を見直し、新しい ADR として記録すること。
本 ADR を取り消さず `Superseded by NNNN` で置き換える運用（§11.6）に従う。

## 影響

- `Location` ヘッダに入る値は必ず `SafeRedirect` 型を経由させる（§9.5）。CSRF の Origin 検証とは
  別の防御だが、同じ「fail-closed・トークンに頼らない」設計方針を共有する。
- 「GET は副作用を持たない」の担保は本節が正本であり、§6.4・§11.4・§12.4-20・§12.4-32 は本節を
  参照する。セッションの `lastSeenAt` 更新のみを唯一の例外とし、ディスパッチャ層でのみ行う。
- **本 ADR は 2026-08-10 の利用者追認により確定した記録である。** `docs/conventions.md` §9.2 の
  要確認 Q41 ブロックは解消され、「CSRF 対策の方式は確定している」という確定記述に置き換わっている。
  §9.2 は本節（0007）を「経緯と却下した代替案の正本」として参照する。将来この方式を見直す場合は、
  本 ADR を取り消さず、後続の ADR で `Superseded by NNNN` を追記して置き換えること。

## 却下した代替案

- **トークン方式（同期トークンパターン。OWASP CSRF Prevention Cheat Sheet の第一推奨）に戻す**:
  全 `<form>` に hidden トークンを埋め、セッションに紐づけて検証する方式。テンプレートとしての実装量が
  増え、生成・埋め込み・検証・失効・多重タブでの扱いをすべて自作することになり、§7.4 の POST 冪等性
  トークンと機構が重複するため却下した。OWASP 第一推奨との差分の詳細と、切り替えるべき場面は上記
  「理由」節を参照。
- **SameSite=Lax + Origin 検証 + トークン方式の併用**: 最も堅牢だが、テンプレートとしての実装量が
  最も増える。fail-closed な Origin 検証の徹底で現実の脅威にほぼ対応できるとの sec-audit の評価により、
  併用までは不要と判断し却下した。
- 上記2案の却下は、2026-08-10 の利用者追認（Q41）により最終確定した。以後、これらの案への回帰は
  新しい ADR の起票を要する。
