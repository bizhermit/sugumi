# 0008. 静的アセットを配信専用 `public/` へ置き、コピー工程を持たない

## 状況

CSS はソースコードとしては `.ts` 側のコンポーネントと同居させたいが、配信もしなければならない。
当初案は「ビルドは `tsc` のみ」（P3）を守るため、`client/src/**` に置いた CSS を静的配信ハンドラが
直接配信する構成だった（要確認 Q40）。sec-audit（H-10）はこれを次の理由でセキュリティ上問題視した。

1. ソースツリーを HTTP ドキュメントルートにすること自体が最小権限に反する。拡張子フィルタの実装
   ミス1つで `client/lib/store.ts` や `apply-fragment.test.ts` が生ソースとして配信されうる。
2. 「テストファイルの出力がブラウザへ配信されない」という担保を `tsc` の `include`/`exclude` に
   求める従来の説明は、ソースツリー直接配信の経路では成立しない（`tsc` の設定が関与しないため）。
   実質、拡張子許可リスト1枚だけが担保になっていた。

この指摘を受けて Q40 として利用者判断を仰ぎ、いったん「起動時に `node:fs` で CSS を `dist/` へ
コピーする」方式（下記の代替案B）へ再裁定した。その後、統括による分析でこのコピー方式自体にも
別のセキュリティ上の欠陥（本番プロセスへの読み書き権限の要求）があることが判明し、コピー工程を
完全に廃止する形で再々裁定した。

## 決定

**CSS は最初から配信専用ディレクトリ `public/assets/<エリア>/client/` に置く。ソースツリー
（`src/<エリア>/client/`）に `.css` を一切置かず、起動時コピーもビルド時コピーも行わない**（§6.6・
§2.1）。

- 配信ルートは `dist/`（tsc の出力。`.js`）と `public/`（配信専用。`.css` とその他静的資材）の
  2つだけに固定する。
- コンポーネント CE（`.ts`）と対応する CSS はパスの一致規則で対応付ける
  （`src/<エリア>/client/components/<相対パス>.ts` ⇔
  `public/assets/<エリア>/client/components/<相対パス>.css`）。対応の欠落は機械検査で双方向に
  検出する（§12.4-39）。
- `src/` に置いてよいのは `tsc` が読むもの（`.ts`）と各プロジェクトの `tsconfig.json` だけとする。
  トランスパイル対象でない資材は用途ごとの直下ディレクトリ（`public/` / `db/`）に置く。

## 理由

- **コピー方式（一時的に採用していた代替案B）が要求する2つの権限がいずれも危険**:
  1. 本番プロセスに**ソースツリーの読み取り権限**を要求する。エリア数に比例して許可パスが増え、
     `--allow-fs-read` に中間ワイルドカードを誘発する。Node 26.5.0 での実測（F16）で、
     `--allow-fs-read=/path/*/client/*` のような中間 `*` は `/path/` 配下を全て true にし、
     以降のパターンを黙って無視することを確認した（エラーも警告も出ない）。
  2. 本番プロセスに **`dist/` への書き込み権限**を要求する。`dist/<エリア>/client/` は本番プロセスが
     実際に配信する実行可能 JS そのものであるため、書き込みを許すと「本番プロセスが自分の配信する
     実行可能 JS を書き換えられる」状態を作り、パス操作の穴1つが全利用者への持続的スクリプト注入に
     化ける。**この危険性は §9.1 の `script-src` の構成方法（当時のパス限定ホストソース・現行の
     nonce 方式のいずれ）にも依存しない**（現行の nonce 方式では、書き換えられたファイルであっても
     応答時に正規の nonce が付与される限り実行されてしまうため、むしろ CSP に頼れない分だけこの
     危険性は大きい。0006 参照）。
- **コピー工程そのものを持たないことで、次がすべて同時に真になる**（コピー方式ではどれか1つが
  必ず崩れていた）。
  - 配信ルートは `dist/` と `public/` の2つだけ。ソースツリーは HTTP ドキュメントルートにならない。
  - `--allow-fs-read` は固定4本で、エリア数・サービス数に比例して増えない（§6.5）。
  - `--allow-fs-write` は `DATABASE_PATH` とその兄弟ファイルだけになる（`dist/` は書き込み不可）。
  - §6.5 の起動時アサート（`process.permission.has(...) === false`）が通る。
  - **固定4本の許可のまま `--conditions=development` を本番へ誤って付けても、`src/` の module load
    が `ERR_ACCESS_DENIED` で即死する**（`getSourceSync` で拒否される。実測 F22）。**サイレントな
    誤起動にはならない**ため、「本番プロセスは `src/` を読まない」という不変条件は権限モデルと
    §12.4-38 の検査の二重で守られる（§6.5・§10.5）。
- **外部ツールを増やさない**（コピー用スクリプトすら要らない）ため、「ビルドは `tsc` のみ」（P3）は
  完全に維持される。当初の懸念（コピー無しでは P3 を守れない）は成立しなかった。
- `*.test.ts` の非配信は `tsc` の `exclude`（§10.3）で担保される（`dist/` に出力されない）。
  `public/` には `.ts` を一切置かないため、CSS 経路にテストコードが混入する余地が構造的に無い。

## 影響

- コンポーネントのファイル構成規約（§11.5）から「1コンポーネント = `.ts` + `.css` の同一ディレクトリ
  並置」という形が失われ、機械的なパス規則と双方向検査（§12.4-39）で代替する必要が生じた。
- `src/` 配下に `.ts` と `tsconfig.json` 以外を置かないという規則（§2.1）は、この裁定を一般化した
  ものである（SQL を `db/` へ出したのも同じ論法。§3.4）。
- サービスが配信してよい名前空間は `ServiceDef.assetNamespaces`（§15.2）の宣言と一致させる。
  **この宣言は「配信してよい範囲」の正本であり、CSP（§9.1）はここから導出しない。**
  「実行してよい範囲」はリクエスト毎の nonce が決める（0006 参照。2026-08-10 の裁定より前は
  `assetNamespaces` が「配信してよい範囲」と「実行してよい範囲」の共通の正本だったが、CSP が
  nonce 方式に変わったことで両者は別々の根拠で別々のことを守る形に分離した。二重管理ではない）。
- パスに `server` セグメントを含むリクエスト（`/assets/<エリア>/server/**`）と `/assets/hosts/**` は、
  実体の有無にかかわらず常に 404 とする規約（§6.6）と組み合わせて、配信対象の絞り込みを行う。

## 却下した代替案

- **A. ソースツリーから直接配信する（当初案）**: 拡張子フィルタの実装ミス1つで `server` レイヤーの
  ソースやテストファイルが生ソースとして配信されるリスクがあり、「テストファイルが配信されない」
  という担保が拡張子許可リスト1枚に依存する構造だったため、sec-audit の指摘（H-10）を受けて却下した。
- **B. `main.ts` 起動時に `client/src/**/*.css` を `dist/client/` へ `node:fs` の `fs.cp` でコピーする**:
  攻撃面は構造的に縮み（ソースツリーがドキュメントルートでなくなる）、いったんはこの案で再裁定した。
  しかし本番プロセスに (1) ソースツリーの読み取り権限（実測 F16 の中間ワイルドカード問題を誘発する）と
  (2) CSP で実行を許可されたディレクトリへの書き込み権限、の両方を要求することが後の分析で判明し、
  「本番プロセスが自分の配信する実行可能 JS を書き換えられる」状態を作ってしまうため、最終的に却下し
  現行案（C）へ再裁定した。
