# 0009. scrypt のパラメータ確定値

## 状況

パスワードハッシュには `node:crypto` の `scrypt`（非同期版必須。§9.3）を使う。規約は当初、
`N=2^17(131072)` / `r=8` / `p=1` / `keylen=32` / `maxmem=192*1024*1024` を**実測前の暫定値**として
掲げていた。パラメータ選定の目標は「実機でのハッシュ時間が 100〜250ms に収まる `N`」であり、
`N` は `node:crypto` の制約で2の冪でしか指定できないため、この目標を実測で確認しないまま暫定値を
確定にできない状態だった。同時実行数（セマフォ相当）の上限も暫定4件のまま根拠が実測されていなかった。

フェーズ1で実測（測定条件: 11th Gen Intel(R) Core(TM) i7-11375H @ 3.30GHz・devcontainer 上 Linux・
Node v26.5.0・2026-08-10）を実施した。

## 決定

**パスワードハッシュのパラメータを次の値に確定する**（§9.3）。

| パラメータ | 値 |
|---|---|
| `N` | `2^16`（65536） |
| `r` | 8（変更なし） |
| `p` | 1（変更なし） |
| `keylen` | 32（変更なし） |
| `maxmem` | `96*1024*1024`（100,663,296。`128*N*r*1.5` で算出） |
| scrypt 同時実行上限 | 4件（値は変更なし。根拠を実測で補強） |

保存フォーマットは `scrypt$N=<n>,r=<r>,p=<p>$<salt(base64url)>$<hash(base64url)>` を維持し、
パラメータを値に同梱する（§9.3）。この設計により `N` を暫定値 `2^17` から確定値 `2^16` へ変更しても、
ログイン成功時の再ハッシュによる既存利用者の移行ロジックはそのまま機能する。

## 理由

**測定条件**: n=30（ウォームアップ3回を破棄）、`r=8`/`p=1`/`keylen=32` 固定、機種は
11th Gen Intel(R) Core(TM) i7-11375H @ 3.30GHz（devcontainer 上 Linux）、Node v26.5.0、
測定日 2026-08-10。時間計測には `scryptSync` を用い、非同期版 `promisify(scrypt)` でも単発コストが
ほぼ一致すること（n=10・128〜158ms のレンジに収束）を別途確認した上で採用した（`scryptSync` 自体の
本番使用は §9.3 で禁止されており、本測定はアルゴリズムの計算コストのみを測る目的で使用した）。

**`N` の実測結果（実測 F28）**

| `N` | 中央値 | 分布（最小〜最大） | p95 | 目標(100–250ms)内か |
|---|---|---|---|---|
| **2^16（採用）** | **135.97ms** | 125.38〜153.24ms | 152.34ms | **全30試行が目標内** |
| 2^17（旧暫定値） | 273.96ms | 260.13〜425.96ms | 316.97ms | **最小値ですら250msを超え、1試行も目標内に入らなかった** |

初回スキャン（n=15、候補 2^14〜2^18の5点）でも同じ傾向が確認されており（2^14=31.15ms・
2^15=73.09ms・2^16=135.78ms・2^17=268.76ms・2^18=566.79ms）、境界にあった2^16と2^17をn=30に
拡大して再測定した結果が上表である。

- **`N` は2の冪でしか指定できない**（`node:crypto` の制約。中間値は `scryptSync('a','b',32,{N:98304,...})`
  等で `ERR_CRYPTO_INVALID_SCRYPT_PARAMS` になることを実測確認済み）。したがって候補は
  2^14/2^15/**2^16**/2^17/2^18の5点飛びに限られ、目標レンジ(100–250ms)に収まる候補は**2^16だけ**
  である。2^15以下は下限(100ms)を大きく割り（2^15の中央値は73ms）、2^17は上限(250ms)を超える。
  中間の値を選ぶ余地は無い。
- **暫定値 `N=2^17` は実測により棄却された。** n=30の実測で中央値273.96ms、最小値ですら260.13msで
  あり、目標上限250msを1度も下回らなかった。
- **`maxmem` は `128*N*r*1.5` の式で算出し、`N` に連動して再計算した。** `N=2^16` では
  `96MiB(100,663,296)`。この式は、規約の旧暫定値 `N=2^17` に対して明示されていた
  `maxmem=192*1024*1024`（=201,326,592）と1バイト単位で完全一致することを確認しており、候補間で
  比較条件が揃っていることの裏づけとした。既定の `maxmem`（32MiB）のままでは `N=2^16` の理論消費量
  64MiB（`128*65536*8`）を超えるため、`maxmem` の明示指定は引き続き必須である。
- **1回あたりの実メモリは64MiBへ半減した**（暫定値`N=2^17`では128MiB）。この余裕は「同時実行数を
  増やす」方向には使わない（本番実機のメモリ予算が未確定なため、安全マージンとして残す）。

**OWASP 推奨組み合わせとの差（sec-audit 指摘 L-1・2026-08-11 利用者裁定）**

OWASP Password Storage Cheat Sheet が例示する scrypt のパラメータ組み合わせ（`N=2^17,r=8,p=1` /
`N=2^16,r=8,p=2` 等）と、本 ADR の採用値（`N=2^16,r=8,p=1`）は**厳密には一致しない**。差分は次のとおり。

| 組み合わせ | 出典 | 本ADR採用値との差 |
|---|---|---|
| `N=2^17,r=8,p=1` | OWASP 推奨例 | `N`が1段階上（本ADRの旧暫定値と同一）。**実測済み**: 中央値273.96ms・最小260.13ms・p95=316.97ms（n=30。測定条件は上記「`N`の実測結果」の表と同一: 11th Gen Intel(R) Core(TM) i7-11375H @ 3.30GHz・devcontainer上Linux・Node v26.5.0・2026-08-10測定） |
| `N=2^16,r=8,p=2` | OWASP 推奨例 | `p`が2倍。**本ADRの測定範囲外**（測定は`r=8`/`p=1`固定で`N`のみを振っており、`p`は振っていない）。scryptの計算コストは`p`にほぼ線形に比例するため`N`を1段上げた場合に近い増分になると見込まれるが、**これは測定条件つきの実測ではなく理論的な見込みであり、本ADRとして数値を断定しない**。実機で確認したい場合は下記「fork利用者がOWASP準拠へ引き上げたい場合」の手順を用いること |

**差を許容した理由（2026-08-11 利用者裁定）**: §9.3 が自ら定める目標100〜250msを優先した。
実測済みの`N=2^17,r=8,p=1`（中央値273.96ms・n=30。測定条件は上表のとおり）はこの目標を外れており、
OWASP推奨組み合わせをそのまま採用すると§9.3の目標と衝突する。本ADRの採用値（`N=2^16,r=8,p=1`）は
§9.3の目標を満たす唯一の候補である（上記「`N`の実測結果」参照）。**OWASP準拠より、自ら実測で定めた
ハッシュ時間の目標を優先する**、という裁定である。

**fork利用者がOWASP準拠へ引き上げたい場合**: 下記「影響」節の再測定手順を用い、`p`（および`N`）を
変えた候補で同じ手順（n≧30・ウォームアップ3回を破棄・中央値/最小/最大/p95）を自分の実機で測定し、
自身のハッシュ時間目標と比較したうえで採否を判断すること。本ADRはその選択を妨げない。値そのものの
正本であり続けるのは本ADRであり、変更する場合は本ADRを取り消さず後続のADRに`Superseded by NNNN`と
記録する（§11.6）。

**同時実行上限（セマフォ相当）4件の実測根拠**

`process.memoryUsage().rss` を20ms間隔でサンプリングしてピークを記録し、`promisify(scrypt)` を
`Promise.all` で同時実行する形で計測した（各水準3試行）。

| 要求した同時実行数 | 実測ピークRSS（`UV_THREADPOOL_SIZE`既定=4） |
|---|---|
| 1 | 約115.7MiB |
| 2 | 約180.0MiB |
| 4 | 約308.2MiB |
| 8 | 約308.4MiB（**頭打ち**） |
| 16 | 約308.6MiB（**頭打ち**） |

- **理由1: libuv スレッドプールの既定サイズ（4）と一致する。** `node:crypto` の非同期 `scrypt` は
  このプール上で走るため、環境変数（`UV_THREADPOOL_SIZE`）を変えない限り真の並列度は4を超えられない。
  要求した同時実行数を8・16に増やしてもピークRSSは4件分（約308MiB）で頭打ちになり、ウォールタイム
  だけが要求数に比例して伸びた。対照実験として `UV_THREADPOOL_SIZE=8` に引き上げた場合はピークRSSが
  約564MiB（8件相当）まで増えることを確認しており、頭打ちの原因がスレッドプールサイズであることは
  実測で裏づけている（推測ではない）。差分はすべて理論値64MiB/件と一致した。
- **理由2: libuv スレッドプールはプロセス全体で共有される。** `fs.promises` の一部API・DNS解決など
  scrypt以外の非同期処理も既定では同じプールを使う。scryptが4スロットを専有すると、他の非同期I/Oが
  同時に詰まりうる。同時実行数を `UV_THREADPOOL_SIZE` と同数（4）に留めることは、scryptがプールを
  独占して他の処理を止める事故を避ける意味でも妥当である。
- **キューイング任せにしてセマフォを省く案は採らない**: セマフォが無いと4件超の要求は待ち行列に
  溜まるだけで503/Retry-Afterを返せず、利用者へのフィードバックと可観測性を失う。libuvのキューと
  アプリ側のセマフォは目的が異なる。
- **`UV_THREADPOOL_SIZE` を引き上げてセマフォも合わせて引き上げる案**は、メモリ消費が比例して増える
  （8件で理論512MiB・実測564MiB）ため、本番のメモリ予算が確定するまで採らない。
- 結論として、**値そのもの（4件）は変えていない。** 本タスクの成果は「未実測の暫定」だった根拠を
  実測で裏づけたことである。

## 影響

- **採用値は暫定値より仕事量が半分になる**（1回あたりの実メモリ64MiB。暫定値128MiBから半減）。
  ハッシュ時間も暫定値の約半分（135.97ms 対 273.96ms）になる。
- **`docs/conventions.md` §9.3 は本 ADR の値へ更新済み**であり、本節の値と食い違った場合は本 ADR を
  正とし §9.3 を直す（§9.3 が明記する取り決め）。
- **本番実機が devcontainer より速い場合、`N=2^16` は100msを下回りうる。** その場合も`N=2^17`へ上げると
  実測比で約2倍のコストになり250msを大きく超える公算が高い（`N`は2の冪でしか選べず中間値が無いため）。
  **どちらを採るかは実機で測り直し、結果を新しいADRに記録すること**（本ADRを取り消さず、後続ADRで
  `Superseded by NNNN` を追記する運用に従う）。
- **再測定の手順（fork利用者・別マシン向け）**: `node:crypto`の`scrypt`を`r=8`/`p=1`/`keylen=32`固定で
  候補`N`ごとに回し、ウォームアップ3回を破棄してからn≧30の中央値・最小・最大・p95を採る。**測定条件
  （n・中央値・機種/CPU・Node版・日付）を添えない値は本書にもADRにも書かない。** 本ADRの数値は
  「11th Gen Intel(R) Core(TM) i7-11375H @ 3.30GHz / devcontainer / Node v26.5.0 / 2026-08-10」固有の
  実測であり、機種やNode版が異なれば数値は変わりうる。本番実機・別マシンでは必ず再測定すること。
- **上記の再測定手順は、OWASP推奨組み合わせ（`N=2^17,r=8,p=1` / `N=2^16,r=8,p=2` 等）へ引き上げたい
  fork利用者にもそのまま使える**（sec-audit指摘L-1・2026-08-11利用者裁定）。`p`を含めて候補を実機で
  測定し、自身のハッシュ時間目標と比較したうえで新しいADRに記録すること。
- 同時実行上限4件は `UV_THREADPOOL_SIZE` の既定値に依存する。将来 `UV_THREADPOOL_SIZE` を変更する
  場合は、本ADRの前提（libuvスレッドプールとの一致）が崩れるため、値の見直しと新しいADRの起票が必要
  になる。

## 却下した代替案

- **暫定値 `N=2^17` の維持**: n=30の実測で中央値273.96ms、最小値ですら260.13msであり、§9.3が定める
  目標100〜250msを全30試行で外れた。`N`は2の冪でしか指定できず中間値を選べないため、目標を満たす
  よう調整する余地が無く却下した。
- **`N=2^18`（さらに重くする）**: 初回スキャンで中央値566.79msと大幅に上限を超えており、検討の対象
  にすらならないため却下した。
- **`N=2^14` / `N=2^15`（軽くする）**: 中央値がそれぞれ31.15ms・73.09msで目標下限100msを大きく割り、
  ハッシュとして弱くなりすぎるため却下した。
- **`UV_THREADPOOL_SIZE` を引き上げて同時実行上限も引き上げる**: 真の並列度を上げられることは対照実験
  で確認したが、メモリ消費が要求数に比例して増える（8件で実測564MiB）。本番のメモリ予算が未確定な
  現段階でメモリ消費を増やす方向の変更を採る理由が無く、却下した。
- **同時実行数の制御をアプリ側セマフォではなく libuv のキューイングに任せる**: セマフォを省くと超過分
  は待ち行列に溜まるだけで503/Retry-Afterを返せず、利用者へのフィードバックと可観測性を失うため
  却下した。
- **OWASP 推奨組み合わせ（`N=2^17,r=8,p=1` / `N=2^16,r=8,p=2` 等）の採用**（sec-audit 指摘 L-1）:
  2026-08-11 に利用者が改めて検討し、現状維持（`N=2^16,r=8,p=1`）を裁定した。§9.3 が自ら定める
  目標100〜250msを優先したためであり、`N=2^17,r=8,p=1`は実測で目標を外れている（中央値273.96ms・
  最小260.13ms・n=30）。差分の詳細・測定条件・fork利用者向けの引き上げ手順は上記「理由」節
  「OWASP推奨組み合わせとの差」を参照。
