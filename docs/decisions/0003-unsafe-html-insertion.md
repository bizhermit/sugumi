# 0003. 断片適用を `Unsafe` 版へ統一（代償措置と承認の経緯）

## 状況

制約 P5（サーバー出力は常に「素の HTML 断片」に統一する＝出力不変則）と、Custom Elements +
Declarative Shadow DOM（DSD）の採用を両立させると、次の衝突が生じる（§1.1 X4）。

1. 断片に DSD（`<template shadowrootmode>`）が含まれうる。
2. `innerHTML` は DSD を解釈しない。解釈するのは `setHTMLUnsafe` / `parseHTMLUnsafe` 系のみ。
3. 安全版 `setHTML()` / `streamHTML()` の既定サニタイザが `shadowrootmode` 属性を通すかどうかは、
   本評価時点で公式文書に明記が無く未解決だった。

安全版を使う場合はサニタイザの挙動が確認できるまで DSD を断片から排除する必要があり、DSD を排除すると
描画ロジックがサーバー・クライアントに二重化して出力不変則から外れる。この二者択一を解消する必要が
あった。

## 決定

**`Unsafe` 版に統一する**（層2 = `setHTMLUnsafe`、層3 = `streamHTMLUnsafe`。§4.6）。断片への DSD の
混入を許可し、安全版への統一は行わない。

代償として、次を**恒久的な必須規約**として同時に定める（安全版へ将来移行しても外せない）。

1. `applyFragment()` に渡してよいのは自サーバーの応答のみ。§9.4 の受け入れ条件（同一オリジン・
   `Content-Type: text/html`・`X-Partial` の値が `full-reload` でない・ステータス2xx/422・
   `data-region` 一致・リダイレクト後の region 一致・`X-Partial-Mode` が既知の値）を、型と実行時
   チェックの両方で強制する。第三者由来 HTML・`postMessage` 由来・URL 由来の文字列を渡すことを
   applier の入口で禁止する。
2. XSS 防御の主防衛線をサーバー側の文脈別エスケープに置く（§6.1 が正本。`Html` の公称型化と
   `attrUrl` のスキーム許可リストの2つが門番）。
3. CSP（`script-src 'nonce-…' 'sha256-…'` / `object-src 'none'` / `base-uri 'none'`）を必須で併用する
   （§9.1。`script-src` の具体的な構成とホストソースを一切置かない理由は 0006 が正本）。
4. HTML 挿入シンクを `applyFragment()` だけに閉じ、CE が属性変更で shadow root を再描画する経路も
   含めて `src/platform/client/dom.ts` の入口（§6.2）に一本化する。`*HTMLUnsafe(options)` 呼び出しでは
   `runScripts: false` を明示指定する（§4.5）。
5. **「層2のみ安全版へ移行する」という退避路は持たない。** 当初は「フェーズ3の先頭で
   『既定サニタイザが DSD を通すか』を実測する余地を残す」としていたが、**2026-08-10 に前倒しで
   実測し（実測 F30）、結果は「不可」で確定した**（既定サニタイザは `<template>` を要素ごと除去し、
   `id` / `class` / `data-*` の一般属性も除去する）。**フェーズ3での再実測は行わない**（影響節も参照）。
   なお、仮に実測が通っていたとしても上記1〜4は不要にならない（クライアント側サニタイザは
   属性値のエスケープ漏れを救うが、`Html` 型の穴も `attrUrl` の穴も救わない）。

## 理由

- `setHTMLUnsafe` / `parseHTMLUnsafe` は `innerHTML` と同様に、挿入された `<script>` を実行しない。
  「Unsafe」は「サニタイザを通さない」の意であり「スクリプトが走る」の意ではないため、この設計における
  残存シンクは実質2つ（インラインイベントハンドラ属性、`javascript:` 等の URL 属性）に限定できる。
  前者は nonce ベース CSP（`'unsafe-inline'` を含めない）で、後者は `attrUrl` のスキーム許可リストで
  塞ぐ（§4.6）。
- サーバーが唯一の描画実装になり、層2（`setHTMLUnsafe`）と層3（`streamHTMLUnsafe`）のセマンティクスが
  完全一致する。代替案（断片から DSD を排除し安全版を使う）は描画ロジックがサーバーとクライアントに
  二重化し、出力不変則（P5）から外れる。
- 層3（`streamHTMLUnsafe`）は `Html` 型の門を通らない（`ReadableStream` を直接受けるため）。層3で
  断片を守っているのは §9.4 の出所検査だけであり、型による保証は無い。この非対称性を承知の上で層3を
  「任意の上乗せ」に留める設計とした（§4.7）。
- **本決定は sec-audit の当初の承認では「条件付き」だった。** sec-audit が提示した追加条件
  （H-08 / H-09 / M-01 / M-06）を全件充足したことを実物照合で確認した時点（T0-11）で、sec-audit は
  無条件承認へ切り替えた。承認の根拠は「残存シンクが2つに限定されていること」と「型で守れない範囲
  （層3のストリーム・応答由来の断片）を本書が明示していること」の2点であり、この2点を崩す改訂を
  行う場合は sec-audit を再度通す必要がある。

**F30 による前提の解消（2026-08-10 実測。付録B-1）**

状況節で「未解決」としていた「安全版の既定サニタイザが `shadowrootmode` 属性を通すか」という点は、
2026-08-10 の実測（F30。実測環境: Node v26.5.0 / Chromium (Chrome for Testing) 149.0.7827.55 /
Playwright (Python) 1.61.0 / 11th Gen Intel Core i7-11375H @ 3.30GHz / devcontainer 上 Linux）で
解消した。

- **実測結果**: `setHTML()`（既定サニタイザ）は `<template>` を**要素ごと除去する**。`shadowrootmode`
  の有無に関係なく、`<template>` 自体が既定の許可要素リストに無いためである。**さらに `id` / `class` /
  `data-*` のような一般属性も除去される。**
- したがって問題は「DSD が通らない」ことにとどまらない。**安全版は DSD 以前に、本書が前提とする
  HTML の形（`id` による region 特定を含む）すら保持できない**（§4.4 の region 特定は `id` に依存する）。
- **この結果は Q2（`Unsafe` 版統一）の決定を追認する材料であり、決定は変わらない。** むしろ起票時に
  「未解決」としていた懸念が、より深刻な形で裏づけられた。
- **同時に「層2のみ安全版へ戻す余地」は実測で消えた。** 上記「決定」節5で残していた「フェーズ3の
  先頭で実測する余地」は 2026-08-10（フェーズ1）に前倒しで実施され、結果は「不可」に確定した。
  Sanitizer の設定変更では救えず、独自の許可リスト設計が要る（そのコストは `Unsafe` 版＋§9.4 の
  受け入れ条件を上回る）。フェーズ3で再実測する動機は無い。

## 影響

- クライアント側の HTML サニタイザによる多層防御を失い、XSS 防御はサーバーのエスケープ（§6.1）と
  CSP（§9.1）の2層に一本化される。
- §9.4 の7条件（同一オリジン・`Content-Type`・`X-Partial`・ステータス・`data-region` 一致・
  リダイレクト後の region 一致・`X-Partial-Mode`）は、本決定の代償措置として全件必須である。条件を
  1つでも緩めると、Unsafe 版統一の前提そのものが崩れる。
- `docs/spec/behavior.md` 等で「既定サニタイザによる DSD 通過」を実測できた場合でも、上記の恒久的
  必須規約は外せない旨を明記すること。
- **上記 F30 の実測（2026-08-10）により、決定節5の「フェーズ3の先頭で実測する余地」は完了・解消
  した。** 層2のみ安全版へ移行するという選択肢は消えており、恒久的必須規約（決定節1〜4）を見直す
  前提も生じない。将来ブラウザの許可要素リストが変わり `<template>` の除去が解消された場合は、新しい
  実測結果として新しい ADR に記録すること（本 ADR を取り消さず `Superseded by NNNN` で置き換える。
  §11.6）。

## 却下した代替案

- **断片から DSD を排除し、安全版（`setHTML` / `streamHTML`）を使う**: クライアント側サニタイザが
  効く一方、断片内の新規コンポーネントはクライアント側 CE が shadow を構築することになり、描画ロジックが
  サーバーとクライアントに二重化する。断片が「素の HTML」から「データ＋クライアントテンプレート」へ
  ずれ、出力不変則（P5）から外れるため却下した。
- **フェーズ3の先頭まで判断を先送りし、「既定サニタイザが DSD を通すか」の実測結果を待ってから決める**:
  判断を先送りできる一方、同型実装の要否というアーキテクチャ上の分岐点がフェーズ3まで確定しないため
  却下した（代わりに、実測してから安全版へ移行する余地だけを設計に残した＝上記の必須規約5）。
