## 0. この文書の位置づけ

本書は「どの URL がどの画面か」の一覧表を提供する。**表の行集合は、全サービスの
`ServiceDef.routes` と `(サービス, メソッド, パス)` をキーとして完全一致することを機械検査する**
（規約 §12.4-42）。現時点では全サービスの `routes` が空配列であるため、本書の表も0行である。

---

## 1. 本表の書式規約（機械検査が前提とする形）

- 表は本書に**1つだけ**置く。サービスごとに表を分けず、単一の表に「サービス」列を持たせる
  （規約 §11.8）。
- 列は次の**6列・この順で固定**する（規約 §11.8。列順を変えない）。

  `| サービス | メソッド | パス | 認可 | 主 region | ハンドラ |`

  - `サービス` ＝ `ServiceDef.name`
  - `メソッド` ＝ `RouteDef.method`
  - `パス` ＝ `RouteDef.pattern` の `pathname` を**バッククォートで囲み、文字単位で一致**させる
  - `認可` ＝ `public` / `authenticated`（`RouteDef.access`。規約 §6.4）
  - `主 region` ＝ `RegionName` の値。断片を返さないルートは `—`
  - `ハンドラ` ＝ `<ファイルパス>:<シンボル名>`
- 「用途」「成功時の遷移先」「主なエラー応答」「備考」など人手維持の列を足してよいが、
  **上記6列を先頭に、この順で置く**（機械検査は先頭6列だけを見る。規約 §11.8）。
- 行の並びは **サービス名 → パス → メソッド の昇順**とする（並びも機械検査の対象。規約 §11.8）。
- **空欄を作らず `—`（全角ダッシュ）を書く**（規約 §11.8）。
- **静的配信（`/assets/**`）はこの表に載せない**（ルートテーブルの外にあるため。規約 §6.4 / §11.8）。
