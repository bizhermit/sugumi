## 1. このテンプレートが提供するもの（要約）

sugumi は、runtime 依存ゼロ・バンドラ不使用で動く、SSR ファーストの3層プログレッシブエンハンスメント
（PE）構成の汎用 Web アプリテンプレートである。サーバーは常に「素の HTML 断片」だけを出力し
（出力不変則。規約 §4.2）、JavaScript の有無・機能差はクライアント側の適用処理だけが吸収する。
層1（JS 無効相当）だけで全機能が完結し、層2・層3は体感速度の上乗せに過ぎない
（規約 §4.1）。認証（セッション・パスワード）・CSRF 対策・CSP を含む共通のセキュリティヘッダ・
多重送信防止つきのフォーム送信・複数マイクロサービス構成を、テンプレートの一部として同梱する。

参照実装の画面・機能そのもの（ログイン＋タスク CRUD 等）は `reference-app.md` の担当であり、
本書には書かない（規約 §11.8 の裁定表）。

> 現段階の注記: 2〜8章はフェーズ2〜3で実装に合わせて記述を追加する。
> 現時点で確定しているのは本節・9章・10章の内容のみである。中身の無い節に
> 「規定が無い」という意味は無い（規約 §11.8。未完成の文書は冒頭にその旨を明記する規約に倣う）。

## 6. エラー時の挙動

### 6.1 HTTP ステータスと画面の対応表

| 状況 | ステータス | 層1 | 層2/3 |
|---|---|---|---|
| 入力検証失敗 | 422 | フォームページを再描画 | 断片を適用する |
| 未認証 | 303（ログインページへ） | リダイレクト | 降格（full-reload） |
| 認可失敗 | 403 | エラーページ | 降格（full-reload） |
| 対象が存在しない、または他利用者のもの | 404 | エラーページ | 降格（full-reload） |
| 予期しない例外 | 500 | 汎用エラーページ | 降格（full-reload） |

- ステータス・応答の形の**正本は規約 8.3**である。本表は対応関係の要約であり、値・属性は本表を
  正本としない。
- 「存在するが、その利用者のものではない」リソースへのアクセスは 404 に丸める（存在確認を漏らさない
  ため。規約 8.3）。403 を返すのは「認証済みだが、その機能そのものへの権限が無い」場合に限る。

### 6.2 層ごとのエラー表現

サーバーはどのステータスでも region の断片を返せる（出力不変則）。層2/3 でこれらのエラー断片が
画面に直接現れることはない。すべて `X-Partial: full-reload` が付き、降格の受け入れ条件（規約 9.4）で
弾かれるためである。断片を返す理由は、層1が同じ URL をフルページとして描画する際に同じ region 関数を
再利用するためである（規約 8.3）。降格時にクライアントが表示する固定文言は規約 14.1 の4件に限られる。

### 6.3 利用者に見せない情報

エラー応答の公開メッセージには固定文言のみを含め、リクエスト由来の値・内部識別子・リソース名・
件数を含めない（規約 8.3）。`APP_ENV` によって応答内容を変える分岐は存在しない（開発時専用の
詳細出力は無い）。

## 7. 起動と停止の動作

起動時に環境変数を一括検証してから listen する（fail fast）。検証に失敗した場合は、不足・不正な
キー名のみを標準エラー出力に出して終了する（値は出力しない。正本は規約 6.5）。`SIGTERM` / `SIGINT`
受信時は新規接続の受付停止 → 定期処理の停止 → 進行中リクエストの完了待ち（上限あり）→ DB 接続の
クローズ → 終了、の順で処理する（graceful shutdown。正本は規約 6.5）。

## 9. このテンプレートが「やらないこと」

★fork 判断に最も効く節。README はこの節への1行 + リンクに留める（規約 11.6）。

- **同梱 `node:sqlite` 実装は単一ノード（単一プロセス）前提であり、水平スケールを想定していない。**
  「サーバーはステートレスで水平スケール可能」という設計方針と、同梱の SQLite 実装は
  そのままでは両立しない（規約 1.1 X3）。`SessionStore` はインターフェースとして抽象化されているため
  設計上は差し替え可能だが、**水平スケールのための実装・移行手順は本テンプレートに含まれない**
  （要確認 Q28。本節は制限の明記に留め、手順は書かない）。
- **層3（DPU 経由の適用）は実験的経路である。** pre-standard の Web プラットフォーム機能であり、
  特定ブラウザの実験的フラグを有効にした場合のみ動作する（正本は規約 4.7）。CI の必須テスト対象にも
  含まれない。本番運用は層1・層2の組み合わせを前提とし、層3の動作を要件にしないこと。
- **1プロセスに複数サービスをマウントする構成（`src/hosts/dev/` 相当）は本番構成の既定ではない。**
  開発時に全サービスを1コマンドで起動する用途と、資源が限られた小規模運用向けの経路であり、
  本番の既定構成は「サービスごとに別プロセス・別ポート」である（正本は規約 15.5）。
- **単一ホスト名でサービスを同居させる公開形態（形態B）は、同じ権限レベルのサービスを束ねる場合に
  限って採る。** Cookie はポートで分離されないため（RFC 6265 8.5 節）、単一ホスト名の下では
  セッション Cookie が全サービスのリクエストに送られ、あるサービスの XSS が同一オリジンの他サービスへ
  波及しうる。**管理画面と一般画面のように権限レベルが異なるサービスを分離したい場合は、
  既定の形態A（サブドメイン分離）を採ること**（正本は規約 15.6）。
- **CORS には対応しない。** 本設計は完全に同一オリジンで閉じており、`Access-Control-Allow-*` を
  含む CORS 関連ヘッダは一切付与しない（規約 9.1）。他オリジンからの API 利用を前提とした構成には
  向かない。
- **ロールベースの認可（RBAC）や OIDC 等の高度な認可基盤は持たない。** ルートの認可区分は
  「未認証で到達してよいか（`public`）」「有効なセッションが必須か（`authenticated`）」の2値に限られる
  （正本は規約 6.4）。ロール・スコープ単位の粒度が必要な場合は、この2値の上に独自に構築する必要がある。
- **DB スキーマのバージョン管理付きマイグレーション（up/down・履歴テーブル）は持たない。**
  起動時に `schema.sql` を冪等に適用するだけであり、スキーマ変更の履歴管理は初期スコープ外である
  （正本は規約 3.4。方式そのものは要確認）。
- **サーバー側のストリーミング応答（チャンク送出）は行わない。** nonce 管理とエラー時の扱いが
  複雑になるため初期スコープでは実装せず、結果として層3のストリーミング機能は実利をほぼ持たない
  （正本は規約 6.3 / 4.7）。
- **1レスポンスで複数 region を同時に差し替えることはできない。** 断片応答は常に単一の region に
  限られる（正本は規約 6.3。要確認 Q33）。
- **楽観的更新は行わない。** すべての書き込みはサーバー応答を待って画面に反映する（正本は規約 7.4）。
