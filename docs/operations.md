## 2. 環境変数

### 2.1 変数一覧（名前 / 必須・任意 / 意味 / 例）

**どんなキーがあるかの正本は規約 §6.5 の設定項目表である。本節はその一覧・意味・例を運用者向けに
展開したものであり、既定値・上限・検証規則は書かない**（正本は規約 §6.5。規約 §12.4-49 が
本節・規約 §6.5・`.env.example`・実装が読むキー集合の一致を機械検査する対象になる）。

複数サービスを1プロセスにマウントする host（`src/hosts/dev/` 相当）では `PORT` / `BASE_URL` の
代わりに `PORT_<SERVICE_NAME>` / `BASE_URL_<SERVICE_NAME>` の形を使う（正本は規約 §15.3）。
`<SERVICE_NAME>` はサービス名の大文字表記であり、現時点では `APP` / `ADMIN` の2つに展開される。

  受け付けない。正本は規約 §6.5）。host ごとにどちらの形式を使うかは4章を参照。

### 2.2 `--env-file` の使い方と、実値を書いてよい場所・書いてはいけない場所

- 読み込みは `node --env-file=.env` を前提とする（正本は規約 §6.5）。`.env` はリポジトリに
  コミットしない。`.env.example` はプレースホルダのみでコミットする（規約 §11.6）。
- **実値（実ホスト名・実ポート・実際の秘密値）を書いてよいのは、運用環境に配置する `.env`
  ファイル本体だけである。** 本書・`.env.example`・`docs/spec/**` のいずれにも実値を書かない
  （規約 §11.8）。
- 環境ごとの値は `.env` ファイルを増やさず、`--env-file` に渡すファイルの場所を環境ごとに変える
  ことで表現する（`.env.production` のような派生名は作らない。正本は規約 §6.5）。

### 2.3 本番で必ず変える値

- `APP_ENV` を `production` にすること。`production` では `BASE_URL` に `https:` スキームが必須になる
  （検証規則の正本は規約 §6.5）。
- `DATABASE_PATH` を運用環境の実際の配置場所に合わせること（規約 §6.5 の「リポジトリ外を既定とし、
  リポジトリ内に置く場合は `*.db` 命名を必須とする」規約に従うこと）。
- `TRUST_PROXY` はリバースプロキシ配下でのみ `true` にすること。既定は `false` である
  （直接インターネットに公開する構成で `true` にすると、クライアント IP とプロトコル判定が
  攻撃者の申告値に従う。正本は規約 §6.5）。

## 4. プロセスの起動

### 4.1 host 単位の起動コマンド

プロセスの単位は `src/hosts/<name>/` である（正本は規約 §15.1）。現時点で同梱している host は
`app` / `admin`（単一サービス）／`dev`（複数サービスをマウントする開発・小規模運用向け経路。
正本は規約 §15.1 / §15.5）の3つである。起動コマンドの実体は `package.json` の
`start:app` / `start:admin` / `start:dev` を参照すること（規約 §12.4-50 の突合対象）。

### 4.2 権限設定（`--allow-fs-read` / `--allow-fs-write`）と、増やしてはいけない理由

`node --permission` の許可範囲は**固定4本**（`<repo>/dist/`・`<repo>/public/`・
`<repo>/package.json`・`<repo>/db/schema.sql` の読み取り）＋ `DATABASE_PATH` とその WAL / SHM
ファイルへの書き込みのみであり、サービス数・エリア数が増えても本数は増えない。
**中間ワイルドカードを書かないこと。** 途中に `*` を書くと、最初の `*` より前の接頭辞が
丸ごと許可される実装差が確認されている（正本は規約 §6.5 の実測 F16）。増やしてはいけない理由
（`.env` を含めない・`dist/` / `public/` に書き込み権限を与えない、を含む）の正本は規約 §6.5 /
§15.5 である。**`--permission` そのものの付け忘れは起動時アサートで検出される**（規約 §6.5）。

### 4.3 graceful shutdown の確認方法

`SIGTERM` / `SIGINT` を送った際、新規接続の受付停止 → 定期処理の停止 → 進行中リクエストの完了待ち
（上限あり）→ DB 接続のクローズ → プロセス終了、の順で進むことを確認する（手順の正本は規約 §6.5）。

## 7. 公開形態とリバースプロキシ

公開形態（ホスト名の分け方）の正本は規約 §15.6 である。

- **形態A（既定・推奨・サブドメイン分離）**: サービスごとに別ホスト名を割り当てる
  （`<app サービスのホスト名>` / `<admin サービスのホスト名>` のようにサブドメインで分ける）。
  Cookie とセッションはホスト名ごとに分離され、サービス間で越境しない（規約 §15.6）。
- **形態B（許容・単一ホスト名 + パス構成）**: 採る場合、`/assets/services/<name>/**` を
  対応するサービスへ振り分け、`/assets/platform/**` と `/assets/services/<name>/**` 以外の
  業務パスのみ運用者が定める接頭辞規則で振り分ける（正本は規約 §15.5 / §15.6）。
  **この形態は「同じ権限レベルのサービスを束ねる場合」に限る**（`behavior.md` 9章を参照）。
  管理画面と一般画面のように権限レベルが異なる場合は形態A を採ること。
