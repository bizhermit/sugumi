# ログイン制限

[目次](index.md)

ログイン失敗が続くと、接続元かアカウントのどちらかで、しばらくログインできなくなる。
どちらが起きたかは、監査ログで分かる。

| 制限                                  | 監査ログ          | 解除                                                      |
| ------------------------------------- | ----------------- | --------------------------------------------------------- |
| [接続元ごとの制限](#接続元ごとの制限) | `address_blocked` | [接続元ごとの制限の解除方法](#接続元ごとの制限の解除方法) |
| [アカウントロック](#アカウントロック) | `account_locked`  | [アカウントロックの解除方法](#アカウントロックの解除方法) |

回数や期間は、アプリサーバーの `docker/.env` の `LOGIN_*` で変更できる（「[環境変数](env.md#アプリサーバーdockerenv)」）。すべてのアプリサーバーで同じ値にする。

## 接続元ごとの制限

同じ接続元からログインに `LOGIN_IP_MAX_FAILED_ATTEMPTS` 回失敗すると、`LOGIN_IP_LOCKOUT_MINUTES`
の間、その接続元からはログインできない。制限を始めると、監査ログに `address_blocked` が出る。

防げないこと・気をつけること：

- 回数は、最初の失敗から `LOGIN_IP_WINDOW_MINUTES` ごとに数え直す。
  - 期間ごとに上限未満の回数で試し続ける攻撃は、止められない。遅くなるだけ。
- NAT の裏のユーザーは、同じ接続元として数える。
  - 同じ NAT の中の誰かが失敗を重ねると、ほかのユーザーもログインできなくなる。
- IPv6 は `/64` ごとに数える。
  - それより広い範囲（`/48` など）を持つ攻撃者は、`/64` を変更しながら試せる。
- 多数の接続元から分散して試す攻撃は止められない。
  - 監査ログの `login_failed` の件数を監視し、急に増えたら気付けるようにする。
- 制限中もパスワードの検証と同じだけ CPU を使う。
  - レスポンスまでの時間から、制限中だと分からないようにするため。
  - 大量のリクエストを抑えるには、ロードバランサーで `POST /login` の頻度を制限している（「[レート制限](load-balancer.md#レート制限)」）。

## アカウントロック

同じアカウントでログインに `LOGIN_MAX_FAILED_ATTEMPTS` 回続けて失敗すると、`LOGIN_LOCKOUT_MINUTES`
の間、そのアカウントはロックされる。ロックすると、監査ログに `account_locked` が出る。

- ユーザー名さえ分かれば、誰でも失敗を重ねて本人を締め出せる。
  - 接続元ごとの制限では、多数の接続元から分散して試されると止められない。
- そのため、ログインに成功した端末を `LOGIN_DEVICE_DAYS` 日の間覚えておく（Cookie `__Host-device`）。
  - 覚えている端末からは、ロック中でも、接続元が制限されていてもログインできる。
  - その端末からの失敗は、アカウントではなく端末ごとに数える。`LOGIN_MAX_FAILED_ATTEMPTS`
    回失敗した端末は、ほかの端末と同じ扱いになる。
  - 監査ログの `login_succeeded`・`login_failed` の `trustedDevice` が `true` なら、覚えている端末からの試行。
- 新しい端末や、Cookie を削除したブラウザからは、ロック中はログインできない。
  - ユーザー名を推測しにくくすると、締め出されにくくなる（連番やメールアドレスを使わない）。
- `LOGIN_MAX_FAILED_ATTEMPTS` を 0 にすると、ロックせず、端末も覚えない。

## 接続元ごとの制限の解除方法

制限の期間が過ぎるのを待てないときに行う。DB サーバーの `/opt/myapp-db` で、監査ログの `address_blocked` の `blockedAddress` の値を指定して、DB の行を削除する。

```sh
docker compose --env-file .env exec -T db \
  psql -U app -d app -c "DELETE FROM app.login_throttles WHERE address = '192.0.2.1'" 2>&1 | cat -v
```

- 管理者（`admin`）ではなく `app` で接続する。アプリを乗っ取られていたときに、仕込まれたトリガーなどが管理者の権限で動かないようにするため。
- 出力は `cat -v` に通す。仕込まれたトリガーなどが出すメッセージの制御文字で、端末を操作されないようにするため。

確認方法：`DELETE 1` と出て、その接続元からログインできる。

## アカウントロックの解除方法

本人を確認したうえで、ロックの期間が過ぎるのを待てないときに行う。DB サーバーの `/opt/myapp-db` で、監査ログの `account_locked` の `accountId` の値を指定して、失敗回数を削除する。

```sh
docker compose --env-file .env exec -T db \
  psql -U app -d app -c "UPDATE app.accounts SET failed_attempts = 0, locked_until = NULL WHERE id = 1" 2>&1 | cat -v
```

- `app` で接続し、出力を `cat -v` に通す理由は、「[接続元ごとの制限の解除方法](#接続元ごとの制限の解除方法)」と同じ。
- リポジトリから DB に接続できる環境では、`deno task account:unlock <accountId>` でも解除できる。

確認方法：`UPDATE 1` と出て、そのアカウントでログインできる。
