# ロードバランサー

[目次](index.md)

HTTPS を受け、アプリサーバーへ振り分ける。1 つだけ置く。
[docker/lb/compose.yaml](../lb/compose.yaml) で nginx（[docker/lb/nginx.conf](../lb/nginx.conf)）を起動する。アプリサーバーと同じサーバーに置いてもよい。

アプリは HTTP で待ち受け、Cookie に Secure を付けているので、HTTPS を受けるロードバランサーを通さないとログインできない。

## ロードバランサーの役割

[docker/lb/nginx.conf](../lb/nginx.conf) が次のことを行う。値を変更するときは、[nginx.conf](../lb/nginx.conf) を書き換えてイメージを再ビルドする（「[イメージのビルド方法](build.md)」）。

| # | 行うこと                                                                   | 詳しく                                                        |
| - | -------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 1 | HTTPS を受け、アプリサーバーへ振り分ける。HTTP は HTTPS へリダイレクトする | [振り分け先の変更方法](#振り分け先の変更方法)                 |
| 2 | 接続元 IP アドレスを X-Forwarded-For で渡す。ユーザーが送った値は渡さない  | [接続元 IP アドレスの受け渡し](#接続元-ip-アドレスの受け渡し) |
| 3 | 遅い接続を打ち切り、リクエストボディを 1 MB までにする                     | [タイムアウト](#タイムアウト)                                 |
| 4 | 接続元ごとに、リクエストの頻度を制限する                                   | [レート制限](#レート制限)                                     |

- ユーザーの本当の接続元を見るため、ホストのネットワークで動かす（`network_mode: host`）。
  ポートを公開する形では、環境によって（Docker で IPv6 を有効にしていないときの IPv6 の接続など）、接続元が Docker のゲートウェイのアドレスになる。
- 振り分け先のアプリサーバーが落ちていると、そのサーバーをしばらく外し、ほかのサーバーへ送る（`max_fails`・`fail_timeout`）。
  外すのは、実際のリクエストが失敗したときだけ。定期的に確認する機能は、無料版の nginx にはない。

## ロードバランサーの構築方法

構築するときに 1 回だけ行う。アプリサーバーを用意した後に行う。

前提条件：「[イメージのビルド方法](build.md)」で、イメージをレジストリに置いてある。ロードバランサーに Docker と Docker Compose が入っている。HTTPS 証明書がある。

1. ディレクトリを作成し、リポジトリの [docker/lb/compose.yaml](../lb/compose.yaml) と [docker/lb/.env.example](../lb/.env.example) を置く。
   イメージをビルドしたのと同じコミットのものを使う。`.env.example` は `.env` にコピーし、値を書く（「[ロードバランサー（.env）](env.md#ロードバランサーenv)」）。

   ```sh
   sudo install -d -o "$USER" /opt/myapp-lb
   cd /opt/myapp-lb
   cp .env.example .env
   chmod 600 .env
   ```

2. 振り分け先のアプリサーバーを、`upstream/servers.conf` に書く（例：[docker/lb/servers.conf.example](../lb/servers.conf.example)）。

   ```nginx
   server 10.0.1.11:3000 max_fails=3 fail_timeout=10s;
   server 10.0.1.12:3000 max_fails=3 fail_timeout=10s;
   ```

   - アドレスは、アプリサーバーの `APP_LISTEN_ADDRESS` にする。
   - 同じサーバーのアプリで、`127.0.0.1` で待ち受けているなら、`server 127.0.0.1:3000;` にする。

3. HTTPS 証明書を、`certs/fullchain.pem`（中間証明書を含む）と `certs/privkey.pem` に置く。
   - 証明書の入手と更新（Let's Encrypt など）は、運用で決める。更新したら、「[振り分け先の変更方法](#振り分け先の変更方法)」と同じく設定を読み直す。

   ```sh
   install -d -m 700 certs
   install -m 644 fullchain.pem certs/fullchain.pem
   install -m 600 privkey.pem certs/privkey.pem
   ```

4. レジストリにログインする（「[イメージのビルド方法](build.md)」の手順の 2 と同じ）。

5. 起動する。ポート 80 と 443 で待ち受ける。

   ```sh
   docker compose --env-file .env up -d
   ```

6. すべてのアプリサーバーで、`docker/.env` の `TRUSTED_PROXIES` を書き、再起動する（「[接続元 IP アドレスの受け渡し](#接続元-ip-アドレスの受け渡し)」）。

確認方法：

- ブラウザで HTTPS の URL の `/login` を開くと、ログインの画面が出る。HTTP の URL は HTTPS へリダイレクトされる。
- 「[接続元 IP アドレスの受け渡し](#接続元-ip-アドレスの受け渡し)」の確認方法。

## 振り分け先の変更方法

アプリサーバーを足したり外したりするときに行う。ロードバランサーの `/opt/myapp-lb` で行う。

1. `upstream/servers.conf` を書き換える。
2. 設定を確認してから、読み直す。読み直しても、処理中のリクエストは切れない。

   ```sh
   docker compose --env-file .env exec lb nginx -t
   docker compose --env-file .env exec lb nginx -s reload
   ```

- アプリサーバーを足すときは、先に「[アプリサーバーの構築方法](setup.md#アプリサーバーの構築方法)」を終える。

確認方法：`nginx -t` が `syntax is ok` と `test is successful` を出し、`/login` が開ける。

## 接続元 IP アドレスの受け渡し

構築するとき、またはロードバランサーやアプリサーバーの配置を変更したときに行う。

ロードバランサーの裏では、アプリから見た接続元はすべてロードバランサーになる。

- 接続元は、監査ログと、ログイン失敗回数（`LOGIN_IP_MAX_FAILED_ATTEMPTS`）に使う。
- すべてロードバランサーのままだと、誰かが失敗を重ねるだけで、全員がしばらくログインできなくなる。

ロードバランサー（[nginx.conf](../lb/nginx.conf)）は、X-Forwarded-For を接続元だけで上書きして渡す。
アプリがそれを使うよう、すべてのアプリサーバーで、`docker/.env` の `TRUSTED_PROXIES` に、アプリから見たロードバランサーのアドレスを書く。

| ロードバランサーの配置                                 | `TRUSTED_PROXIES`                              |
| ------------------------------------------------------ | ---------------------------------------------- |
| 別のサーバー                                           | ロードバランサーのアドレス                     |
| 同じサーバーで、アプリが `127.0.0.1` で待ち受ける      | `APP_NETWORK_GATEWAY` と同じ値                 |
| 同じサーバーで、アプリがサーバーのアドレスで待ち受ける | そのサーバーのアドレス（`APP_LISTEN_ADDRESS`） |

- カンマ区切りで複数書ける。CIDR（例：`10.0.1.0/24`）でも書ける。
- IPv4 は `/8`、IPv6 は `/32` より広い範囲は書けない（起動時にエラーになる）。
- 書いたら、アプリを再起動する（`docker compose --env-file docker/.env up -d`）。

確認方法：ブラウザの拡張機能などで `X-Forwarded-For: 192.0.2.1` を付けてログインする。
アプリサーバーの `docker compose --env-file docker/.env logs app` の監査ログで、`remoteAddress` が自分のアドレスになることを確認する。

- `192.0.2.1` なら、ロードバランサーがユーザーの送った値をそのまま転送している（[nginx.conf](../lb/nginx.conf) を変更していないか確認する）。
- ロードバランサーのアドレスなら、`TRUSTED_PROXIES` が合っていない。表示されたアドレスを `TRUSTED_PROXIES` に書く。

## タイムアウト

アプリの時間制限（「[アプリの時間制限](env.md#アプリの時間制限)」）を変更したときに見直す。

アプリのタイムアウトは、アプリまで届いた接続にしか効かない。ロードバランサーでも、遅い接続を打ち切る（[nginx.conf](../lb/nginx.conf) の `client_header_timeout`・`client_body_timeout`・`send_timeout`、接続元ごとの同時接続数の `limit_conn`）。

- nginx は、リクエストボディを受け取り終えてからアプリに送る（デフォルトの `proxy_request_buffering on`）。
  - ボディを少しずつ送ってくる接続は、アプリではなく nginx が受け持ち、上の設定で打ち切る。
- `client_max_body_size` は、アプリのリクエストボディの上限（[src/web/app.ts](../../src/web/app.ts) の `MAX_BODY_BYTES`）と揃える。
- `proxy_read_timeout` は、`DB_CONNECTION_TIMEOUT_SECONDS` と `DB_STATEMENT_TIMEOUT_SECONDS` の合計より十分に長くする。
  - 短いと、アプリが 503 を返す前に nginx が 504 を返す。

## レート制限

ユーザーの数が大きく変わったときに見直す。

アクセスログは、ログインなしで送れるリクエスト（静的ファイル・404 を含む）にも 1 行ずつ出る。
大量に送られると、アプリや DB の負荷に加えて、次のことが起きる。

- `log-forwarder` がためる量の上限（`LOG_BUFFER_MAX_SIZE`）を超え、送信先が止まっている間のログが捨てられる。
- CloudWatch の取り込みの費用が増える。ログ用サーバーでは、ディスクが埋まる。

そのため、[nginx.conf](../lb/nginx.conf) で接続元ごとに頻度を制限し、超えたら 429 を返す。

| 対象               | 頻度（`rate`） | 一時的に超えてよい数（`burst`） |
| ------------------ | -------------- | ------------------------------- |
| すべてのリクエスト | 20 回／秒      | 100                             |
| `POST /login`      | 10 回／分      | 5                               |

- 値は、画面を開いたときに読み込むファイルの数やユーザーの数に合わせて決める。
- NAT の裏のユーザーは同じ接続元として数えるので、ユーザーの数に合わせて余裕を持たせる。
- `POST /login` を厳しくするのは、アプリが、接続元ごとの制限中もパスワードの検証と同じだけ CPU を使うため（「[接続元ごとの制限](login-limits.md#接続元ごとの制限)」）。
- 頻度は、ロードバランサーの中で数える。ロードバランサーは 1 つなので、アプリサーバーの数によらない。

## 接続元を偽装される条件

アプリは、`TRUSTED_PROXIES` のアドレスから届いた X-Forwarded-For を信用する。次の場合は接続元を偽れる。
偽れると、接続元ごとのログイン制限をすり抜けたり、ほかのユーザーのアドレスに制限をかけたりできてしまう。

- `TRUSTED_PROXIES` にロードバランサー以外のアドレスを含めたとき：その範囲の端末は、X-Forwarded-For を書いて送れば偽れる。
  ロードバランサーのアドレスだけを書く。
- ロードバランサー上のほかのプロセス：アプリのポートに直接つなぐと、ロードバランサーと同じアドレスから届くので偽れる。
  信頼できない OS のアカウントやサービスを、ロードバランサー（同じサーバーならアプリサーバーも）に置かない。
- アプリのポートを、ロードバランサー以外からも届くようにしたとき：`TRUSTED_PROXIES` の範囲と重なる経路があると偽れる。
  アプリのポートは、ロードバランサーのアドレスからだけ受け付ける（「[アプリサーバーの構築方法](setup.md#アプリサーバーの構築方法)」の手順の 1）。
