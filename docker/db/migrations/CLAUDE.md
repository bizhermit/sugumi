# docker/db/migrations/

DB スキーマの変更（マイグレーション）。`docker/db/bin/db-migrate` が、DB ユーザー `migrator` で適用する。
実行方法は、開発はルートの `CLAUDE.md`、本番は `docker/README/migration.md` を参照。

## ファイル

- ファイル名は「4 桁の番号_説明.sql」（英小文字・数字・`_`・`-`）。番号は `0001` から欠けずに続ける。
  - 番号が `schema_migrations` のバージョンになる。
- 適用済みのファイルは書き換えない。適用済みかどうかは番号で決まるので、書き換えても適用し直されず、DB ごとに中身が食い違う。
- 取り消すときは、打ち消すマイグレーションを新しく足す。down は作らない。
- 足したら、`src/lib/db.ts` の `SCHEMA_VERSION` を最後の番号に上げる。
  - アプリは起動時にこれと DB のバージョンを突き合わせ、違えば起動しない。
  - 上げ忘れは `tests/lib/db_test.ts` が検出する。

## 書けること・書けないこと

- 適用していないファイルを番号順に、すべて 1 つのトランザクションで、PL/pgSQL の `EXECUTE` で実行する。1 つでも失敗すると、すべて元に戻る。
  - `COMMIT`・`ROLLBACK` などのトランザクションの操作は書けない。
  - psql のメタコマンド（`\` で始まる行）は書けない。
  - トランザクションの中で実行できない文（`CREATE INDEX CONCURRENTLY`・`VACUUM` など）は書けない。
- 拡張の追加など、管理者の権限が要る変更は書けない。DB サーバーで管理者が実行する。
- 時間制限はかけない。終わるまでテーブルをロックしたままになる。

## 権限

`migrator` が作ったテーブル・シーケンスには、`app`（アプリ）の読み書きの権限が自動で付く（`docker/db/init/10-app-role.sh`）。

- スキーマを足すときは、同じマイグレーションで `GRANT USAGE ON SCHEMA <スキーマ> TO app` を実行する。
- 読ませるだけにしたいテーブルは、`REVOKE` で権限を外す（`schema_migrations` と同じ）。
- 関数には PUBLIC の EXECUTE が付く。`SECURITY DEFINER` の関数は `REVOKE EXECUTE ... FROM PUBLIC` をする。
  しないと、`app` が `migrator` の権限で実行できてしまう。

## データの変更

マイグレーションは、開発・テスト・CI・本番のすべての DB に、空の DB にも、同じ順番で 1 回ずつ適用される。
どの DB に適用しても同じ意味になるデータの変更だけを書く。

- 書いてよいもの：スキーマの変更と組になるデータの変更。
  - 既存の行の移し替え・補完（列を分ける、型を変える、新しい NOT NULL の列に値を入れるなど。`0004_sessions_log_id.sql` が例）。
  - アプリが前提にする固定のデータ（区分の値など）。アプリのコードと一緒にバージョンが進むもの。
- 書かないもの：特定の環境の行だけを直す、一度きりの修正（障害対応で、本番の決まった id の行を直すなど）。
  - ほかの DB では、何もしないか、別の行を書き換えてしまう。新しく作る DB でも、毎回実行され続ける。
  - 条件にメールアドレスなどを書くと、個人の情報がリポジトリに残る。
  - こうした修正は、DB サーバーで `app` として手で行う（`docker/README/login-limits.md` の解除と同じ方法）。
- 多くの行を書き換えるときは、本番と同じくらいの量のデータで、かかる時間を先に測る。
  更新の間はアプリを止めているので、その時間だけ停止が延びる。
